# Pipeline (HR portal v1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the HR-portal Pipeline (a lifecycle kanban plus per-project conversations and member-only notifications) without degrading login, HR report submit, Link History or accounts.

**Architecture:** The feature adds new `pipeline_*` tables and one new `NotificationType` value, `PIPELINE`, served by `/v1/pipeline/*` on the existing Express API. That API has its own 3-connection Prisma client, its own bulkhead, its own rate-limit buckets and a router-local error mapper. The HR portal polls one consolidated `POST /v1/pipeline/sync` about every 10 s while a view is visible, using commit-ordered cursors. Everything ships **dark** behind `pipeline.mode` in `system_settings`, then goes to a named pilot, then to GA.

**Tech Stack:** Express 4 + Prisma 5.22 (raw SQL for hot paths) + Postgres 16, Zod validators in `@dashmani/shared`, Next.js 14 App Router (apps/hr), `@dnd-kit/core` + `@dnd-kit/sortable`, and Vitest (run from `apps/api`).

**Source of truth:** `docs/superpowers/specs/2026-09-26-pipeline-design.md`, cited below as **§n** for Part 2 sections, **Pn** for prerequisites, **Mn** for milestones and **route #n** for the §3.4 table.
- The spec already contains the exact models, SQL, route contracts, lock order, rate limits and UI rules.
- This plan names every file, sequences the work into shippable PRs, and fixes the tests and verification for each task.
- When a step says "implement per §x", the code must match that section exactly.

## How to run things (read once)

**Branching.** Each PR below branches from `origin/main`:
```bash
git fetch origin && git checkout -b <branch> origin/main
```

**Test database.** Never use the dev DB: `tests/setup.ts` TRUNCATEs it. This is a one-time setup:
```bash
docker exec dashmani-db psql -U user -d postgres -c "CREATE DATABASE dashmani_test"
```
After any `schema.prisma` change, push the schema to the test DB:
```bash
cd packages/db && DATABASE_URL=postgresql://user:password@localhost:5432/dashmani_test npx prisma db push --skip-generate && cd ../..
```
Expected output: `Your database is now in sync with your Prisma schema.`

**Run one test file.** `apps/api/vitest.config.ts` never overrides an env var you set yourself:
```bash
cd apps/api && DATABASE_URL="postgresql://user:password@localhost:5432/dashmani_test?connection_limit=1" npx vitest run tests/pipeline/<file>.test.ts
```

**Full API suite** (the same command without a file). Baseline: all green.
```bash
cd apps/api && DATABASE_URL="postgresql://user:password@localhost:5432/dashmani_test?connection_limit=1" npx vitest run
```

**Frontend checks.** Never build while dev servers are running.
```bash
npx tsc --noEmit -p apps/hr/tsconfig.json && npx tsc --noEmit -p apps/internal/tsconfig.json && npm run build
```

**API typecheck.**
```bash
npx tsc --noEmit -p apps/api/tsconfig.json
```

**Commit messages** end with:
```
Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>
```

**Deploy windows.** Merge only between 11:00–16:00 IST on a working day. Never 09:00–10:00 (login rush) or 17:30–00:30 (the HR submit rush). Merging to `main` deploys to production.

  function stripTagsLinear(s: string): string {
    let out = "", i = 0;

      const lt = s.indexOf("<", i);
      if (lt === -1) { out += s.slice(i); break; }
      const gt = s.indexOf(">", lt + 1);
      if (gt === -1) { out += s.slice(i); break; }   // regex: unmatched "<" is kept verbatim

      i = gt + 1;
    }

  }
